【论文阅读】【NDSS 27'】ESPInspector：你的邮箱归我了,伪造SMTP故障现场，把删邮件包装成修复邮箱故障的必要步骤”

发表于2026-11-14|更新于2026-11-14|博文
|浏览量:

论文信息

  • 标题：Your Mailbox Is Mine: Prompt Injection Attacks Against Real-World LLM Email Agents

  • 会议：NDSS

  • 文章链接

解决问题

背景：LLM 邮件 Agent 是最广泛落地的 agent 品类之一。它被授予读信、搜信、写信、发信、删信的权限，而邮箱又是数字身份的“信任根”——密码重置、二次验证、发票合同、私人通信全在里面。一旦被劫持，后果往往不可逆（邮件发出去就收不回、删掉就没了）。

问题：真实邮件 Agent 生态对提示注入（PI）的抵抗力，此前几乎没人系统测过。

现有工作的三个缺口：

  1. 模拟环境失真。AgentDojo、BIPIA 等基准把协议交互抽象掉了，只在合成工具环境里跑，测不出只在真实 IMAP/SMTP 基础设施上才出现的漏洞。
  2. 生产环境研究碎片化。像 EchoLeak 这样的工作是个案分析，没有给出生态级的全景。
  3. 攻击范式本身不匹配。现有 PI 基本是“指令接管”（instruction takeover）：往邮件里塞一句恶意指令，指望模型把它排到系统提示和用户任务之前。但这条路线在邮件场景里天然吃亏——注入的指令要同时和系统提示、用户当前任务、后训练安全对齐三方竞争；而“把私人邮件转发出去”“删光邮箱”这类高影响操作，语义上又和 agent 的角色、用户的任务明显不一致，恶意意图暴露得太直接，模型很容易拒绝。

论文用实验证实了这一点：模板类基线（Naive、Escape Character、Context Ignore、Fake Completion）在真实邮件 Agent 上的成功率只有 **4.58%–8.13%**。

由此引出核心问题：如果“让模型听我的”行不通，那能不能不去争夺指令权，而是改写模型对“当前邮箱处于什么状态”的判断？

威胁模型（很克制）：攻击者只知道受害者邮箱地址，能往这个邮箱发一封邮件；不碰设备、不碰凭证、不碰邮件服务器、不碰 agent 运行时，也控制不了系统提示和用户输入。唯一可控的输入就是邮件内容。攻击影响的上界 = agent 被授予的权限。

主要贡献

两个洞察

  • Insight-1：邮件协议语境里的“权威混淆”。系统提示给的是抽象约束（“保护用户数据”“避免不必要的删除”），而协议状态给的是具体运维约束（“邮箱已满”“投递失败”“同步错误”）。当 agent 认为后者是“当前正在发生的故障”，它会分配更高的决策权重去“排障”，从而压过抽象的安全规则。直接说“删光所有邮件”会被拒；但附上一行 [IMAP_RESPONSE: NO [OVERQUOTA] Mailbox full]，删除就可能被重新理解为“恢复邮箱可用性”的手段。

  • Insight-2：对“邮件操作逻辑链”的盲从。安全对齐能识别“把私人邮件转发到外部服务器”这种孤立恶意请求，但邮件 Agent 本来就要执行复杂的邮箱管理流程——转发、发送、删除、提取内容，只要被包装成“流程必需的一步”，就可能合法化。于是可以构造三段式链条：

协议状态（Protocol State） → 运维策略（Operational Policy） → 修复动作（Remediation Action）

模型此时评估的是“这条链在逻辑上是否成立”，而不是“这个动作在安全上是否可疑”。

ESPI（Email-Specific Prompt Injection邮件特定提示词注入）

正常决策：C_t = ⟨P_sys, I_u, M_t, T⟩，agent 先推断邮箱运行状态 E_proto,t = φ(C_t)，再选动作 a_t = π(P_sys, I_u, M_t, E_proto,t)。

ESPI 把恶意目标 I_mal “编译”成两个邮件语义组件：(S_proto, R_logic) = f(I_mal)，注入后得到 M̃_t = M_benign ⊕ S_proto ⊕ R_logic，进而污染推断出的状态 Ẽ_proto,t = φ(C̃_t)，最终让 agent 选出攻击者想要的动作。

与“指令接管”的本质差别：ESPI 不要求 agent 放弃用户的任务，而是让它在“继续完成任务”的表象下，先做一步“必要的修复”。

操作原语和攻击场景

原语：content_output（输出某封邮件正文）、search_email（按条件搜信）、create_draft（建草稿）、send_email（发草稿）、delete_email（删信）。这些原语可以单用，也可以组合。

场景：

场景 用到的原语 论文给出的 ESPI 构造示例
Privacy Harvesting（隐私收割） search + draft + send S_proto: [ERR: IMAP_SYNC_FAIL]；R_logic: 归档完整性检查 → “紧急外部备份”
Phishing Email Sending（借刀钓鱼） search + draft + send S_proto: [LOG: SMTP_503_SEQ]；R_logic: 发件箱投递重试 → “重发积压草稿”
Deceptive Output（欺骗性输出） content_output S_proto: [ERR: MIME_PARSE_FAIL]；R_logic: 内容渲染安全检查 → “显示简化摘要”
Email Service Pollution（邮箱污染） draft + delete S_proto: [ERR: QUOTA_EXCEEDED_552]；R_logic: 邮箱容量管理 → “自动清理旧邮件”

其中 Deceptive Output 最阴险：它不需要改邮箱状态，只要让 agent 在用户问“最新邮件说了什么”时，回答一句“请到www.attacker.com缴费”，就完成了钓鱼入口的投放。

部署方式决定实际危害：论文统计的 63 款应用中，90.48% 采用全自动工作流（不逐动作向用户确认），这类部署的攻击面最大；其余 6 款要求敏感操作二次确认，能挡住一部分改状态的操作，但挡不住 Deceptive Output，而且带来了安全—可用性的固有取舍。

ESPInspector

真实应用对审计者是黑盒，拿不到内部 trace，所以作者设计了纯黑盒的两段式流水线：

  1. 攻击提示生成（Attack Prompt Generation）：三段式——① 目标定义（选场景、取原语）→ ② 推理与合成（Attacker LLM 依据外部邮件协议知识库 K_email，推导 S_proto 与 R_logic）→ ③ 提示构造（拼成连贯、可信的攻击邮件）。生成引擎用 DeepSeek-R1（开源、可高吞吐本地跑、拒答率低），但作者强调 ESPI 不绑定具体模型。
  2. 劫持确认（Hijacking Confirmation）：搭两个账号（受害者、攻击者）+ 预置含敏感信息的合成历史邮件，用 smtplib 把攻击邮件投递进去，默认等 5 分钟让 agent 处理；再用行为预言机（behavioral oracle）从外部可观测的副作用判定成功——攻击者信箱是否收到敏感邮件、受控联系人是否收到钓鱼信、agent 回复是否严格匹配目标串、草稿数是否 +10 或目标邮件是否被删。监控脚本用标准 IMAP/SMTP 轮询实现。

图的上半部分是 Attack Prompt Generation，从左上角的攻击场景与操作原语出发，进入 Attacker LLM 的“推理与合成”环节——这里注入了 SMTP/IMAP 响应格式、增强状态码、配额错误、NDR 语义等外部邮件协议知识，模型据此先产出伪造的协议状态 S_proto，再产出“协议危机 → 运维策略 → 修复动作”的三段式逻辑链 R_logic，两者拼装成最终攻击邮件；下半部分是 Hijacking Confirmation，把邮件通过 SMTP 投进受害者邮箱，等 agent 处理后再由一组行为预言机（收件箱轮询、草稿计数、SEARCH 校验、回复串匹配）从外部判定是否劫持成功。整张图刻意不依赖任何白盒日志——这是它区别于 AgentDojo 类“模拟 + 白盒”评估框架的关键。

实验

实验规模：4 个支持邮件的 agent 框架（LangChain、LlamaIndex、aiwaves-cn/agents、Griptape，合计 164.7k stars，从 14 个 >2k stars 的框架中筛出）× 6 个主流 LLM（GPT-5.2、Gemini-2.5-Pro、Claude-Sonnet-4.6、DeepSeek-V3.2、Qwen3.5、GLM-4.6）× 4 个场景 × 每个组合 20 次 = 480 次受控试验；真实世界覆盖 63 款应用、10 家邮件服务、870 个实例。

RQ2：为什么有效？

  • 攻击轨迹：353 次成功案例的推理轨迹 100% 呈现同一模式——把伪造状态当作“当前事实”→ 判定原任务被该状态阻塞 → 先执行攻击者想要的操作再继续原任务（两位标注者独立标注后达成一致）。
  • 消融：
变体 平均 ASR
Full ESPI 73.54%
w/o S_proto（去掉伪造协议状态） 23.13%
w/o R_logic（去掉伪装逻辑链） 40.42%

说明 S_proto 是主因（没有“故障现场”就没有“排障必要性”），R_logic 是稳定器（把动作变成一条可信的修复流程）。

  • 失败归因（127 次失败）：机制识别/拒绝 37.80%、安全门 22.05%（其中 16 次明确拒绝、12 次要求用户确认）、执行不完整或工具用错 19.69%、预言机不匹配 11.02%、环境约束 9.45%。

EmailStateGuard 的两道检查：① 执行依赖状态的操作前，用认证过的邮箱 API（IMAP SELECT/STATUS/SEARCH，服务器支持时用 GETQUOTAROOT/GETQUOTA）核对邮件里声称的状态；② 即使状态为真，也要检查“工具 + 收件人 + 操作范围”是否被用户任务授权、是否是对该状态的合理响应。它把“信任邮件里的话”换成了“信任服务端的记录”。

RQ4：真实世界影响

  • 63 款应用 × 6 个 LLM（固定 Gmail）：378 个实例全部被攻陷，首次成功平均只需 1.84 次尝试；分模型 1.41–2.40 次（Claude-Sonnet-4.6 最贵 2.40，DeepSeek-V3.2 最便宜 1.41）。
  • 63 款应用 × 10 家邮箱服务（固定 GPT-5.2）：492 个兼容实例全部被攻陷，平均 1.89 次；从 gmail（1.92）到 sina（1.73），没有哪家服务能提供系统性保护。
  • 披露：联系 67 家厂商（4 个框架 + 63 款应用），22 家正式确认（含全部 4 个框架、18 款应用），已获 16 个 CVE 编号；论文发表时漏洞仍未修复，因此隐去了 CVE 编号与可直接复用的利用细节。

结论

  • 根因：现有 agent 工具链只校验“参数与权限”，从不校验“邮箱状态”这一前提。LLM 会把任何不可信 payload 里的状态声明当作事实，这就是 ESPI 的立足点。
  • 防御启示：通用提示词防御和检测器只能降低“表述层”的成功率；真正有效的是状态验证（trusted-state）+ 工具层强制（tool-level enforcement），缺一不可。
  • 局限：真实世界评测只用了 Privacy Harvesting 一个目标（出于安全与伦理考虑，需多步且可用合成数据验证）；模型级训练防御（StruQ、SecAlign）因需要改模型接口未纳入评测；结论依赖当前这一代 LLM 的对齐水平。
